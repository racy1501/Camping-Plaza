# 总体结论

- **已确认玩法完成度**：约 **60%**。v0.3 已确认规则中，主链路（回合结构、帐篷配置、升级故障、绿化、NPC 流程、两类客源、评价好评率、预定主链、转过夜主链、收入展示、MCP 链路）已形成闭环；但已确认规则中仍有 **6 处实现偏差** 和 **7 项未实现**，集中在：帐篷解锁、NPC 冲突与调解、脾气标签、回访客生成、预定失败次日来客率下降、好评率影响预定概率、SQLite 持久化。
- **运行骨架完成度**：高（约 85%）。MCP 操作链（/mcp/state → /mcp/actions → /api/action → /api/turn/advance）已闭环，多轮定点修复后无阻断性 Bug；唯一骨架级缺口是**无任何持久化**，服务重启全部归零。
- **是否适合进入前端正式制作**：**可以进入，但建议先处理 3 件小事**：① 清理已删除的 AI 移动动画残留；② 修正 `/api/map` 键名契约或更正 README；③ 明确前端数据源（当前 `/api/map` 从未被调用）。
- **是否适合进入数值平衡阶段**：**不适合**。数值平衡依赖规则定案，当前仍有 5 组策划未定项的占位实现（客流公式、转过夜判定、提升服务、好评率公式、故障间隔），且有已确认闭环未补齐。应先补已确认规则 → 再确认未定项 → 最后才做数值验算。

# 部分完成模块

1. **§7 帐篷清洁**：状态流转完整，但执行方错误——设计为 AI 执行（不占决策点、可合并 MCP 调用），代码为后台全自动，清洁作为一项经营动作不存在。

# 实现偏差

1. **清洁执行方（§7）**：设计 AI 执行 → 代码全自动。位置：`_auto_clean_tents()`。
2. **娱乐满意度断链（§9/§14）**：`entertainment_satisfaction` 升级后从不被读取，升级娱乐区对满意度零影响。
3. **Turn 4 顺序（§4/§17）**：设计「回合开始时处理转过夜」→ 代码先 checkin 后转过夜；且 Turn 4 新生成的日间客当天即被判定走/留，无游玩过程。
4. **pending 预定永久滞留（§16）**：不处理则永久阻塞后续所有新预定生成，预定功能无声停摆。位置：`_generate_daily_reservation()`。
5. **AI 移动动画（§3/§21）**：已删除机制仍运行，且读取不存在的后端字段（repairing_tent / managing_facility / ai_action）。
6. **/api/map 契约（README）**：README 声称前端调用 /api/map，实际未调用；两端键名不一致。
7. **satisfaction_bonus 死字段**：升级写入但满意度计算从不读取（实际用 10+level*3）。
